# Harness research synthesis (2026-09-07)

Sources: `scratchpad/research/{harnesses-A,harnesses-B,local-speed-memory,prompt-composition}.md` (all dated 2026-09-07). Answers `docs/plans/harness-line.md`. No new research performed here — every number traces to one of the four reports.

## 1. Executive summary

- **Measured**: Hermes' real fixed prefix is **~20.5-20.6k tokens** cold (`mlx-server.log`, `prompt_tokens=20468-20622, cached_tokens=0`), not the "~18k" round number in CLAUDE.md — cold prefill takes ~25-30s at ~700-810 tok/s. Composition: **34 tool schemas ≈ 55.9 KB JSON ≈ 15,515 tokens** (the single biggest line item — `session_search` 5,919B, `terminal` 5,675B, `delegate_task` 5,556B, `computer_use` 5,183B, `skill_manage` 4,130B), skills index (names+1-line only) ≈ 8,988B ≈ 2,497 tokens, stable-tier prose ≈ 20,138 chars ≈ 5,594 tokens, context tier = 0 for real dashboard sessions (cwd=`~`), volatile tier ≈ 581 chars ≈ 161 tokens.
- **Three biggest levers** (all evidenced in §2/§7): (1) scope the dashboard's `platform_toolsets` — it currently has no `tui` entry and falls back to the full 34-tool default including `browser_*`(7), `computer_use`, `video_analyze`, `vision_analyze`, `project_*`(3), `process` — cutting unused tools for a chat-only surface removes a large fraction of the 55.9 KB tool-schema block; (2) lazy tool/skill catalog (dsh `dsh-tool-skill` pattern: name+description only, `skill(name)` on demand, digest-gated republish) — directly attacks the 15.5k-token tool-schema block, the largest section; (3) drop `computer_use` guidance+schema from non-CUA turns (2,678 chars prose + 5,183B/~1,440 tok schema ≈ 2.2k tokens combined, cheap and immediate).
- **Verdict**: upgrading Hermes Agent (0.18.0 → v2026.8.31, 26,281 commits) is safe to *attempt* on the doc-diff evidence alone (only two behavior changes found, neither touching context/compaction code), but the gap is too large to certify without a real branch attempt gated on the 6-case drill before/after.

Notable per-block cuts inside stable tier: `computer_use` guidance 2,678 chars (~744 tok, only fires when `computer_use` in `valid_tool_names` — true on every platform today per CLAUDE.md's "auto-enabled when cua-driver exists"); `TOOL_USE_ENFORCEMENT_GUIDANCE` 824 chars (~229 tok, config-togglable via `agent.tool_use_enforcement`); `tool_guidance` (MEMORY+SESSION_SEARCH+SKILLS) 1,997 chars (~555 tok, MEMORY_GUIDANCE is the largest of the three); `TASK_COMPLETION_GUIDANCE` 769 chars and `PARALLEL_TOOL_CALL_GUIDANCE` 618 chars (both config-togglable today, defaults True).

**Prefix-instability sources** (things that can defeat the exact-prefix KV cache mid-session):
1. A context-compression event (`agent/system_prompt.py:496 invalidate_system_prompt`) forces a full rebuild — necessarily breaks the exact-prefix match for every subsequent turn until re-primed on the shorter prefix. Triggered by `compression.threshold`.
2. Day rollover changes the date-only `timestamp_line` — but it's near the END of the volatile tier (last), so it does NOT invalidate the earlier system-prompt/tool-schema portion under an exact-prefix scheme; only the small 88-char tail. Not a real hazard.
3. Cross-lane parallel requests (prewarm, background 9B lane, Telegram, For-You) share the same server process but different prefixes; `APC_EXACT_CACHE_ENTRIES=6` caps distinct exact-prefix slots — heavy interleaving of distinct prefixes could evict a still-wanted entry.
4. An external memory-provider block appended to the volatile tier could vary if that provider's state changes (none configured today, so no hit measured).

**Config knobs that matter** (all in `~/.hermes/config.yaml`):
- `compression.threshold` = 0.5 (compress at 50% of the 65,536-token window, ~32,768 tokens), `compression.target_ratio` = 0.2 (compact to ~13,107 tokens), `protect_last_n`=20 / `protect_first_n`=3 verbatim.
- `platform_toolsets`: **no `tui`/dashboard entry exists** — dashboard/serve sessions fall back to the default `["hermes-cli"]` toolset (`hermes_cli/config.py:909`), i.e. the dashboard gets the same 34 tools as a full CLI coding session with zero scoping.
- `agent.tool_use_enforcement` = "auto" (matches model-name substrings; Qwen matches, so the 824-char block fires) — can be set `false` for a well-behaved model.
- Skills dir: `~/.hermes/skills/` (26 top-level dirs); "focus mode" (`coding_context.py::coding_compact_skill_categories`) already demotes non-coding categories to names-only, but names-only is already what ships, so further gains there are capped (~30-40% at most per the report).
- No single global "max tool result length" knob exists — truncation is handled per-tool (e.g. context files use a dynamic cap derived from `model.context_length`).

**Notable specifics that matter for us:**
- Codex CLI's 256-line/10-KiB head+tail (128+128 lines, 5+5 KB) truncation is the most concrete, implementable tool-output policy found, but its own issue tracker documents the failure mode of a fixed global cap breaking full file reads/MCP results (#7906) — make any Hermes equivalent configurable per tool type.
- dsh's digest-gated skill catalog (only republish when membership/description/visibility changes, not every turn) is a direct, cache-preserving answer to Hermes' 2,497-token skills index; dsh's `dsh-output-retention` + `dsh-spill`/`dsh-spill-local` (spill oversized results to a session-scoped 0600 file, hand back a path+retrieval hint) generalizes Codex's truncation into a no-data-loss design.
- OpenHands' `CondensationAction` event makes compaction an auditable transcript entry rather than a silent side effect — maps directly onto Hermes' Flight Recorder.
- Cline's `mcp_lazy`+`mcp_search` reported ~12K→~600 token reduction is illustrative/third-party, not a universal number, but validates the lazy-tool-catalog pattern architecturally.
- Goose's OTel-native tracing (OTLP/HTTP, MLflow/OpenObserve-compatible) is the only harness here with a self-hostable, standard trace format by default.
- Agent Zero v2.11 ships a real, dated, user-visible context/cache-hit meter — cheap pattern to copy; its "Context Doctor" name is a false friend (self-repair, not health-check) and should not be confused with `hermes doctor`.
- Roo Code (the Cline fork) was discontinued May 15, 2026 — its more aggressive tool-output-archiving compaction strategy and manual "condense" button are historical/legacy references only, not a maintained target.
- Pi's system prompt+tools at <1000 tokens (by deliberately rejecting MCP, plan mode, built-in to-dos) is the sharpest existence proof that Hermes' 20.5k tokens is far from a hard floor — but Pi also ships only 4 core tools vs Hermes' 34, so the comparison is architecture-scope-dependent, not a like-for-like target.

## 4. Portable ideas, ranked

Ranked by impact on prompt tokens / TTFT / RAM / trust, divided by effort. Third-party/illustrative numbers are marked "illustrative — not vendor-verified" per the source reports; all others trace to a primary source.

1. **Scope `platform_toolsets` for the dashboard/`tui` surface.** Mechanism: add a `tui` entry to `config.yaml` `platform_toolsets` that drops `browser_*`(7), `computer_use`, `video_analyze`, `vision_analyze`, `project_*`(3), `process` for chat-only turns. Source: prompt-composition.md §2/§5 (measured — dashboard currently has no `tui` entry and falls back to the default `["hermes-cli"]`). Maps onto: `hermes_cli/config.py:909` `resolve_toolset()`, already-existing per-platform config surface. Effect: measurable multi-KB cut of the 55.9 KB tool-schema block; exact figure not measured in the report — **first thing to bench**.
2. **Drop `computer_use` from non-CUA turns.** Mechanism: gate `computer_use` out of `valid_tool_names` for surfaces that don't need it. Source: prompt-composition.md (2,678 chars guidance + 5,183B/~1,440 tok schema, auto-enabled on all platforms today per CLAUDE.md). Maps onto: `agent/system_prompt.py:217-219`, `platform_toolsets`. Effect: ~2.2k tokens off the resident prefix, cheap, immediate.
3. **Digest-gated skill/tool catalog with on-demand load** (dsh `dsh-tool-skill`). Mechanism: publish name+description-only catalog, single `skill(name)`/`tool(name)` call to load full body, republish catalog only when its digest changes. Source: harnesses-B.md §2 finding 3 (primary, local package README). Maps onto: Hermes' existing `skills_list`/`skill_view`/`skill_manage` tools and `<available_skills>` block (already names+1-line, per prompt-composition.md — so this idea applies more directly to the 15.5k-token *tool schema* block than the already-lean skills index). Effect: the 15.5k-token tool block is the largest single item — even a partial (e.g. top-10-by-recency resident, rest on-demand) lazy scheme is the single biggest lever measured; illustrative Cline third-party number (~12K→~600 tok, not vendor-verified) suggests order-of-magnitude headroom exists for MCP-style catalogs generally, though Hermes' 34 first-party tools are a different shape than an MCP marketplace.
4. **Head/tail, tool-agnostic tool-output retention library** (dsh `dsh-output-retention` / Codex's 256-line-10KiB dual cap). Mechanism: `ItemRetainer` (head-only, ordered units — glob/grep) and `TextRetainer` (head/tail/headTail, UTF-8-safe — bash/web_fetch), explicit "truncated ≠ incomplete" marker. Source: harnesses-B.md §2 finding 2; harnesses-A.md Codex #2; local-speed-memory.md §4. Maps onto: Hermes has no single global tool-result cap today (prompt-composition.md §5) — per-tool caps exist ad hoc (e.g. context files). Effect: bounds worst-case prompt blowup from any one tool call; effort medium (needs per-tool mapping).
5. **Spill-to-disk for oversized tool results** (dsh `dsh-spill`/`dsh-spill-local`). Mechanism: write full oversized output to a session-scoped 0600 file, hand the model a path + "use read/grep" hint instead of losing data. Source: harnesses-B.md §2 finding 2. Maps onto: Hermes' Flight Recorder already keeps full text server-side per the brief — this pattern gives the *model* itself a recovery path, complementing (not replacing) the Recorder. Effect: eliminates the "silent truncation makes agents lie" failure mode (local-speed-memory.md §4 dev.to citation).
6. **Compaction as a visible, auditable transcript event** (OpenHands `CondensationAction`). Mechanism: insert an explicit event recording exactly what was condensed/when rather than silently rewriting history. Source: harnesses-A.md OpenHands #1, #4. Maps onto: Hermes' Flight Recorder (undo/audit already exists) and the "conversation size" meter proposed in the brief — natural attachment point. Effect: trust/UX, not token savings.
7. **Prompt-cache-aware compaction that replays the prefix verbatim** (dsh `dsh-compaction-basic`), vs. **Pi's opposite choice** (skip cache writes on one-off compaction calls). Source: harnesses-B.md §2 finding 4, §3 finding 4 — explicit documented contradiction between the two harnesses. Maps onto: Hermes' MLX prompt-prewarm investment (CLAUDE.md: 26s cold → 0.4s cached) makes local prefix-cache misses far more expensive than a cloud provider's marginal cache-write cost — favors dsh's approach for Hermes specifically (report's own reasoning, not measured). Effect: avoids invalidating the exact-prefix APC cache on every compaction event (prompt-composition.md §4 already flags compaction as the one normal-path prefix-cache breaker).
8. **Token-based (not event-count-based) compaction trigger.** Mechanism: OpenHands' own issue tracker (#6707) documents event-count triggers letting the harness "still exceed model max input token limitations" despite condensation running. Source: local-speed-memory.md §7 finding 6-7. Maps onto: Hermes already uses `compression.threshold`=0.5 of `model.context_length` (a fraction-of-context, not absolute-token, trigger) — prompt-composition.md confirms this is already token/fraction-based, so Hermes is already ahead of OpenHands' documented failure mode; item retained as a **verification** task (confirm the trigger truly measures tokens, not event/message count, end-to-end).
9. **`hermes-assistant doctor`** (brief's own ask, corroborated). Mechanism: one command/Settings card checking services, model lanes, venv pins, FDA, disk, tokens present, index state, last release check. Source: harnesses-A.md Codex `codex doctor` (config/model/MCP/sandbox checks); harnesses-B.md confirms Hermes Agent upstream *already ships* `hermes_cli/doctor.py` in 0.18.0 (installed). Maps onto: existing Settings cards architecture (aux_* module pattern, CLAUDE.md). Effect: cheap, trust-building; low token/RAM effect.
10. **Context/cache-hit meter in the chat header** (Agent Zero v2.11 "Context Window Usage Indicator"). Mechanism: live token usage, remaining space, provider cost, cache-hit status. Source: harnesses-B.md §4 finding 2 (official, shipped, dated). Maps onto: `mlx-server.log` already logs `prompt_tokens`/`cached_tokens` per request (prompt-composition.md §3) — the data exists, only the UI surface (a dashboard header meter, per the brief) is missing. Effect: trust/UX; cheap given data already logged.
11. **Event-sourced, crash-safe session log with synthetic closers on resume** (dsh `dsh-session-persistence-jsonl`). Mechanism: an unclosed trailing turn is closed (synthetic `TOOL_NOT_STARTED`/`TOOL_OUTCOME_UNKNOWN` + `turn/end{interrupted}`) rather than truncated or left invalid. Source: harnesses-B.md §2 finding 5. Maps onto: Flight Recorder's crash-recovery semantics (unverified whether it already does this — worth checking). Effect: reliability, not token savings; medium-high effort.
12. **OTel-shaped tracing export** (Goose's default, brief's own "Tracing export" 1.2.3 item). Source: harnesses-A.md Goose #7. Maps onto: Flight Recorder → JSONL/OTel export, self-hosted (MLflow/OpenObserve-compatible), fits "local-first" better than a SaaS. Effect: observability, not tokens.
13. **Formal additive-only plugin compatibility contract with deprecation window** (Hermes Agent upstream's own new policy). Source: harnesses-B.md §6. Maps onto: Hermes Assistant's own MCP server (`dashboard/hermes_mcp.py`) — cheap written-policy adoption now, pays off if/when that surface needs to evolve without breaking Claude-side integrations.
14. **Name-based canonical-session registry instead of stored session-id pointers** (Hermes Agent upstream Bot Mode lesson — five prior incidents from pointer-based designs). Source: harnesses-B.md §6. Maps onto: any future "one persistent chat per bot/persona" feature (Telegram gateway, Quick Ask) — a design lesson, not a code port.
15. **Transactional self-update pipeline: plan→snapshot→apply→restart→verify→report with machine-readable receipts** (Hermes Agent upstream). Source: harnesses-B.md §6. Maps onto: Hermes Assistant already has a self-updater (`aux_update.py`, `update.sh`) — directly portable checklist regardless of whether a full Hermes Agent version upgrade happens; upstream explicitly built each stage because "its absence was a real field failure."

## 5. Local speed and memory: actions

Merged, de-duplicated from `local-speed-memory.md` "What Hermes Assistant should do" blocks, with evidence and caveats.

**Prefill / TTFT**
- Prefill is **compute-bound (FLOPs), not memory-bandwidth-bound** — quantization does not speed it up; token count is what dominates. Cutting the system prompt from ~18-20.5k to ~6k tokens should cut prefill time roughly proportionally (derived, not independently verified for Qwen3-class specifically). Caveat: no official Apple/mlx-lm-published prefill table for Qwen3 9B/27B 4-bit was found — measure in-house at 6k/12k/18k-token prefixes via `mlx_lm.cache_prompt` (or mlx-vlm equivalent) before/after any trim, on Hermes' actual hardware, before trusting any third-party number (§1 findings 1-7, all flagged medium confidence, single-practitioner benchmarks).
- Adopt `save_prompt_cache`/`load_prompt_cache` to persist the resident system-prompt prefix as a `.safetensors` cache file, reloaded at wake instead of recomputed. **Caveat: this is documented for mlx-lm; Hermes runs mlx-vlm 0.6.14 for the primary lane — verify API availability/parity in mlx-vlm before relying on it** (not confirmed in the report).
- KV quantization (`QuantizedKVCache`, group_size 64/bits 8, ~halves KV memory per an mlx-examples PR) is available at the cache-object/`generate()` level but **not yet exposed as an `mlx_lm.server` CLI flag** (open issue #1043) — pending, track before adopting.
- Check whether `--prompt-cache-bytes`/`LRUPromptCache` (mlx-lm server's own in-memory LRU) is already engaged for the fixed prefix, independent of the compaction work.

**Lazy catalogs**
- Convert the tool-schema block (largest section, 15.5k tokens) to a two-tier structure: index resident, full schema/skill body on demand — mirrors Anthropic's Tool Search Tool pattern (defer_loading, ~500-token search tool, vendor-reported "85% token overhead reduction" for a 147-tool/90k-token MCP case — **self-reported, not independently reproduced**) and Claude Agent Skills' three-tier progressive disclosure (header→body→reference files, corroborated across 3 independent sources for the architecture, though the specific "500 tok → 2,000 tok instead of 70,000" ratio is one promotional-titled blog's illustrative estimate).
- Hermes' skills index is *already* names+1-line-only (prompt-composition.md confirms), so this idea's remaining leverage for Hermes is mainly on the **tool-schema** side, not skills.

**Memory layers**
- Prefer a **minimal, verifiable design**: recent verbatim turns + a small set of durable facts with recency-decay, retrieved via BM25/FTS — not a vector DB / LLM-extraction pipeline. Two direct pieces of evidence: (a) **"Verbatim Chunks Beat Extracted Artifacts"** (arXiv 2601.00821) directly challenges Mem0/Letta-style fact-extraction memory for at least some conversational tasks (single paper, title/abstract-level claim only — not independently reproduced); (b) **Mem0/Letta/Zep are validated only against frontier-scale cloud LLMs** — none of the sourced material discusses running their own extraction/consolidation LLM calls on a small local model (Qwen3-9B/27B), which would compete for the same GPU/wired-memory budget as the main agent loop. Mem0's own "90% token cost cut" claim is self-reported/marketing.
- If semantic retrieval is ever added, use a small dedicated embedding model (Letta precedent: "BAAI/bge-small-en-v1.5") separate from the main chat model, not the 27B itself.
- Borrow Zep's "prompt-ready Context Block" pattern conceptually: pre-format memory into a small fixed-shape block ("Known facts:"/"Recent notes:") rather than raw retrieval hits, keeping prompt growth bounded regardless of underlying store size.
- Given Hermes already has an FTS5 index (`aux_index.py`) and no vector DB, this design is directly buildable with existing infrastructure — no new dependency required.

**Tool-result budgets**
- Adopt a fixed byte/line budget (~10 KiB or token-equivalent) with head+tail preservation and an explicit "[...N lines omitted...]" marker as a day-one default; prefer **token-based over byte-based** from the start (Codex's own community is mid-migration from byte→token, issue #6426 — Hermes can skip that churn).
- For large/must-not-lose outputs, spill to file + hand back a retrieval hint rather than truncate silently (Codex issue #14206, dsh's shipped spill packages).

**Idle / unload / memory policy**
- Set `iogpu.wired_limit_mb` explicitly rather than relying on macOS's conservative default (measured default GPU-addressable fraction varies 16-18GB-of-24GB down to "7.04GiB out of reach" on one M2 Max — direction consistent, exact numbers vary by RAM/macOS version). Hermes already does RAM-aware ceiling tiering (CLAUDE.md "RAM-AWARE DEFAULTS") — this is a related but distinct OS-level knob, worth auditing against.
- **MLX's own internal ceiling (1.5× Metal recommendation or 95% of installed RAM, whichever lower) can exceed the OS wired-limit default** — a single detailed practitioner source, not independently verified against MLX source, flagged as an asymmetric risk specific to MLX (vs. llama.cpp, which reportedly fails safe first). Worth a direct verification pass against Hermes' actual hardware before treating as settled.
- mlx-lm's server manages only the *prompt* cache's memory, not whole-model idle-unload — LM Studio (60min JIT TTL default) and Ollama (`keep_alive`, default 5min, `OLLAMA_MAX_LOADED_MODELS` LRU eviction) both have first-class idle-unload; Hermes' idle-suspend loop already implements an equivalent (CLAUDE.md) — this confirms the harness must own model lifecycle itself, not expect it from mlx-lm/mlx-vlm.

**Small specialist models for routing**
- **Routing/classification accuracy at sub-1B scale is directly contradictory across sources** (one report: ~90% accuracy for LoRA-tuned Qwen2.5-0.5B on routing; another: 24.8% accuracy for the same model class zero/few-shot) — do not adopt either number; run an in-house eval (50-100 labeled examples) on Hermes' actual skill/tool-routing decisions with Qwen3-0.6B/1.7B before building a tiny-classifier lane.
- If adopted, budget latency additively — a multi-step router+downstream pipeline measured ~1.45-1.5s vs. a bare router at ~0.3-0.5s in one source; compare against just letting the 9B/27B decide via an in-prompt menu, since a heuristic/regex router may remain competitive for a small, keyword-separable skill set.
- If embeddings are added, Qwen3-Embedding-0.6B or nomic-embed-text-v2 (137M) are the better-fitted cheap tier vs. Qwen3-Embedding-8B (reported "25x slower...roughly 45x the memory" for likely-unneeded quality on a short local fact store).
- All throughput numbers in this section (525 tok/s Qwen3-0.6B, 44K tok/s embedding server, etc.) are single-practitioner or vendor self-reported and explicitly flagged as needing in-house re-measurement on Hermes' exact hardware/model/quant combination before being used to justify RAM/latency budgets.

**Compaction (local-model specific)**
- Use a **fraction-of-context-window** trigger, not an absolute token count copied from Claude's 150k/50k defaults (which assume a 200k+ context window a local Qwen3 deployment doesn't have) — Hermes' `compression.threshold`=0.5 of 65,536 already does this correctly per prompt-composition.md.
- Keep the compaction trigger **token-based**, not event/turn-count-based, to avoid OpenHands' documented failure mode.
- Log actual before/after token counts on every compaction event (mirroring Claude's own documented example format) to get real production compression-ratio numbers rather than assuming any vendor's illustrative ratio (e.g. Claude's ~50x example) transfers.

## 7. Proposed 1.2.x plan

**1.2.0 — system-prompt diet + doctor**
Concrete cuts (from §2, prompt-composition.md), each to be measured before/after against the ~20.5-20.6k baseline:
- Add a `tui`/dashboard entry to `platform_toolsets` dropping `browser_*`(7), `computer_use`, `video_analyze`, `vision_analyze`, `project_*`(3), `process` for chat-only turns — measure resulting tool-schema JSON size (bytes) and prefill tok/s vs. baseline.
- Gate `computer_use` guidance+schema out of non-CUA platforms — measure the ~2.2k-token delta directly.
- Set `agent.tool_use_enforcement: false` if Qwen3.8-27B proves well-behaved in the drill — measure the 824-char/229-tok delta.
- Total target: report's own framing is "≥30% fewer prefix tokens" (from the brief) — sum the above cuts against the measured ~20,470-token baseline and report the actual percentage achieved, not an assumed one.
- `hermes-assistant doctor` (script + Settings card): services, model lanes, venv pins, FDA, disk, tokens present, index/needsyou/onboarding state, last release check.
- **Measure**: cold TTFT/prefill tok/s before/after (via `mlx_lm.cache_prompt` timing or mlx-vlm equivalent, in-house, not third-party numbers), tool-schema JSON byte count before/after, doctor command coverage (does it catch the failure modes CLAUDE.md documents, e.g. stale idle-suspend marker, mlx-vlm version drift).

**1.2.1 — tool-result budgets + compaction surface + context/cache-hit meter**
- Tool-result budgets: head/tail retention (dsh-style `ItemRetainer`/`TextRetainer`, or Codex-style dual line+byte cap), token-based not byte-based, plus spill-to-disk for oversized results.
- Compaction surface: expose `compression.threshold`/`target_ratio` in Settings › Agent & Models with measured token savings; make condensation events visible in the transcript (OpenHands `CondensationAction` pattern) so the Flight Recorder can log them as auditable/undoable.
- Context/cache-hit meter in the chat header, built from data `mlx-server.log` already logs (`prompt_tokens`/`cached_tokens`) — no new instrumentation needed, only a UI surface.
- **Measure**: worst-case single-tool-call token blowup before/after the budget; number of times spill-to-disk fires vs. plain truncation; whether the visible-condensation event correctly appears in the Recorder timeline; cache-hit percentage shown to the user against the raw log numbers (sanity-check the UI meter against `mlx-server.log`).

**1.2.2 — memory layer v1**
- Design supported by the evidence in §5: **verbatim recent turns + small durable facts with recency decay, retrieved via the existing FTS5 index (`aux_index.py`)** — not a vector-DB/LLM-extraction pipeline (arXiv 2601.00821's "Verbatim Chunks Beat Extracted Artifacts" finding, plus the unverified-on-small-local-models gap for Mem0/Letta/Zep). Format memory as a small fixed-shape "what I know about you" block (Zep's Context Block pattern) rather than raw retrieval hits.
- **Open question**: whether any semantic/embedding layer is worth adding at all given Hermes has no vector DB today — if added, use a small dedicated embedding model (Qwen3-Embedding-0.6B or nomic-embed-text-v2), never the 27B, and re-measure its actual local latency/token cost before trusting Mem0's "90% token cut" marketing claim.
- **Measure**: resident prompt tokens for the memory block before/after (brief's own ask), and whether facts retrieved via FTS actually reduce need for full-history replay in practice (not just in theory).

**1.2.3 — evals + tracing export**
- Extend the 6-case drill into a scheduled local eval suite with a history chart (brief's own item).
- Tracing export: Flight Recorder → JSONL/OTel-shaped export (Goose's default pattern, self-hostable, MLflow/OpenObserve-compatible) for external analysis.
- **Open question**: whether Hermes needs a benchmark-style eval (SWE-bench-style, like mini-swe-agent/OpenHands) in addition to the 6-case drill, or whether the drill's scope is sufficient — none of the four reports establish a clear threshold for "when do you need a bigger eval suite."

**1.2.4 — routing v2 (tiny classifier vs. heuristics)**
- **What to measure first, before building anything**: run Qwen3-0.6B/1.7B against 50-100 of Hermes' own labeled skill/tool-routing decisions and compare accuracy directly against the current heuristic/in-prompt-menu approach — do **not** start from either the "90% accuracy" or "24.8% accuracy" third-party numbers (harnesses-B/local-speed-memory both flag this as a direct, unresolved contradiction likely explained by fine-tuning status, which neither source makes explicit).
- Budget latency additively if a classifier lane is added (router + downstream call), and compare the total against the bare in-prompt-menu approach — a heuristic/regex router may remain competitive if Hermes' skill set stays small and keyword-separable.
- **Open question**: whether routing v2 is worth building at all before 1.2.0-1.2.3 land, since the prompt-diet work (1.2.0) may already remove enough of the token pressure that motivates a classifier-based router.
