# 1.2 baseline — the fixed prompt every fresh conversation pays

Measurements taken 2026-09-07 on this Mac (M5 Max, 68 GB), all offline: nothing
here loads or wakes a model, and `pgrep -fl mlx` was unchanged before and after.

## Prompt budget (the toolset diet)

### Why

`~/.hermes/logs/mlx-server.log`, the `cached_tokens=0` lines — i.e. the first
turn of a conversation the prefix cache has never seen:

```
2026-09-05 12:41:19 Prefill completed: prompt_tokens=20509 cached_tokens=0 elapsed=26.077s rate=786.5 tok/s
2026-09-07 11:48:51 Prefill completed: prompt_tokens=20622 cached_tokens=0 elapsed=25.496s rate=808.8 tok/s
2026-09-07 13:44:55 Prefill completed: prompt_tokens=20619 cached_tokens=0 elapsed=28.059s rate=734.9 tok/s
```

**20,468–20,622 tokens at 735–809 tok/s = 25–28 seconds before the first
token**, once per new conversation. Prefill is compute-bound (see
`post-v1-baseline.md`), so tokens ≈ seconds; every later turn in the same
conversation is ~0.2 s off the APC exact-prefix cache. The prefix is fixed, so
this is a pure tax, and the only part of it that is pure configuration is the
tool schemas.

### Two corrections to the obvious plan, both measured

**1. `hermes prompt-size`'s tool figure is not platform-aware.** It is the
ceiling, not this platform's set:

```
cd ~ && for p in cli telegram discord tui; do hermes prompt-size --platform $p --json; done
# tools.count == 34, tools.json_bytes == 55855 for all four
```

`hermes_cli/prompt_size.py::_build_inspection_agent` constructs an `AIAgent`
without `enabled_toolsets`, so `get_tool_definitions(None)` takes the "start
with everything" branch. It also ignores `HERMES_TUI_TOOLSETS` and
`platform_toolsets` entirely — verified with an env pin and, separately, with a
sandbox `HERMES_HOME` whose config carried a `platform_toolsets` entry. So the
after-state has to be measured another way.

**2. The key that matters is `platform_toolsets.cli`, not `.tui`.** Dashboard
chats go through `hermes serve`, and a new session's tools come from
`tui_gateway/server.py::_load_enabled_toolsets`:

1. env `HERMES_TUI_TOOLSETS` (an explicit pin) — `com.hermes.serve.plist` sets
   no such variable;
2. `agent.coding_context.coding_selection(platform="tui")` — returns `None`
   here: the plist's `WorkingDirectory` and the dashboard's own
   `session.create` cwd are both `~`, and `resolve_runtime_mode(...).is_coding`
   is `False` there;
3. the fallback, literally
   `enabled = _get_platform_tools(cfg, "cli", include_default_mcp_servers=True)`
   — **the platform key is hardcoded `"cli"`**, and `hermes_cli/platforms.py`
   has no `"tui"` entry at all.

A `platform_toolsets.tui:` block would therefore be read by nothing. The same
`cli` key also governs `hermes -z` one-shot runs (the chat fallback, briefings,
the watchtower intel pass, For-You) and `hermes` in a terminal — the same agent,
so the diet is consistent, and those runs pay the same prefill.

### The three profiles

**Full** — no `platform_toolsets.cli` entry, or `[hermes-cli]`. The default.

**Balanced** — config name `lean` (it shipped under that name; the key is kept
so an older config still resolves):

```
web, terminal, file, code_execution, skills, todo, memory,
session_search, clarify, delegation, vision, computer_use
```

Dropped: `browser` (12 schemas — the largest toolset), `tts`, `image_gen`,
`video`, `video_gen`, `x_search`, `cronjob`, `homeassistant`, `spotify`,
`discord`, `discord_admin`, `yuanbao`, `context_engine`. `computer_use` stays:
the dashboard's screen-control cards are a product feature.

**Focused** — config name `focused`. Balanced minus the three remaining
heavyweight single-tool schemas, `session_search` (5,871 B), `delegation`
(5,544 B) and `computer_use` (5,159 B):

```
web, terminal, file, code_execution, skills, todo, memory, clarify, vision
```

What you give up, stated the way the card states it: **screen control,
sub-agents, and past-conversation search from inside a chat.** Nothing in the
dashboard breaks — the conversation list, the Settings search and the local
FTS5 index are dashboard features that never go through an agent tool, and
`aux_recorder`'s `TOOL_KIND` table falls through to `"other"` for a tool that is
no longer offered. This is the profile for someone who chats; it is the one that
clears the ≥30% target.

Checked against `dashboard/*.py` and `dashboard/*.js` (plus
`expanders_extra.py`, `hermes_mcp.py`) for every dropped tool name: **no
dashboard feature depends on one.** The only hits are `aux_recorder.py`'s
`TOOL_KIND` table, which *labels* `browser_*`/`cronjob` for the Flight
Recorder's undo view and falls through to `"other"` for an unknown tool, plus
coincidental substrings (`browser_download_url` in the GitHub Releases payload,
`watts` in the power widget, `_ix_search` in the local index). Telegram keeps
its own `platform_toolsets.telegram` entry and is untouched.

- One intermediate point, measured but **not** shipped as a profile: Focused

twelve-tool browser toolset. That is Focused, and it is why Focused is a
deliberate third choice rather than the default.

### Applying it

No restart is needed. `_load_enabled_toolsets()` is uncached and runs at agent
construction (per new session), and `hermes_cli.config.load_config()` is
memoised on the config file's `(mtime_ns, size)` — so an edit is picked up by
the very next **new** conversation. Conversations already open keep the agent
they were built with; `POST /api/prompt/budget {"restart": true}` kickstarts
`com.hermes.serve` for anyone who wants it immediately, and the UI warns that
this interrupts a turn in flight.

`hermes config set` is **not** the write path: it stores a list as a quoted
string —

```
$ HERMES_HOME=<sandbox> hermes config set platform_toolsets.tui '["web","terminal"]'
✓ Set platform_toolsets.tui = ["web","terminal"] in <sandbox>/config.yaml
$ grep tui <sandbox>/config.yaml
  tui: '["web","terminal"]'
```

— which `_get_platform_tools`'s `not isinstance(toolset_names, list)` guard then
ignores, silently falling back to the full composite. `aux_promptbudget.py`
therefore does a surgical line-based edit of the `platform_toolsets` block in
the `aux_config.py` house style (stdlib line scanning, no yaml dependency),
after a timestamped 0600 backup, with an atomic replace that preserves the file
mode. A no-op write touches nothing at all — verified byte-identical by
SHA-256, with no backup created.

The estimator above measures the *prompt*. This measures the **wait**, from a
suspended model to a usable answer, which is what the diet is actually for.

## The skills index — headroom found, no config path to it

`agent/prompt_builder.py::build_skills_system_prompt` takes
`compact_categories`, which demotes a whole category to names-only (nothing is
hidden or made unloadable). Measured on this machine's 18 skill categories:

| | Chars |
|---|---|
| As rendered today | 10,622 |
| Compacting the 17 categories unused in 60 days | 4,508 |
| Compacting every category | 3,629 |

That is **6,114 chars ≈ 1,700 tokens ≈ 2.3 s** of headroom — comparable to the
whole toolset diet.

**But no configuration reaches it on this surface.** The only non-test caller is
`agent/system_prompt.py:285`, which gets its set from
`coding_compact_skill_categories()` → `resolve_runtime_mode(...)
.compact_skill_categories()`. That returns a non-empty set only when
`is_coding` is true *and* `agent.coding_context` is `focus`/`strict`/`lean`.
Probed with the dashboard's real parameters (`platform="tui"`, `cwd=~`):
`is_coding` is **False**, so `agent.coding_context: focus` would change nothing
for dashboard sessions. Per the brief, `~/.hermes/hermes-agent` was not patched;
the finding and the numbers ride in `GET /api/prompt/budget` under `skills` and
are reported in the card's payload rather than acted on.

(`prompt-size` reports the skills index as 8,988 chars vs the builder's 10,622:
`prompt-size` filters by the available tools/toolsets. The compaction ratio is
what matters and it is measured on the same builder call either way.)

## Conclusion

Config-only cuts are worth about **10 %** at the safe default: `browser` was the
only heavy toolset Balanced drops, because **ten of the thirteen dropped
toolsets were already 0 bytes** — unmet `check_fn`s had kept them off the wire
all along. Getting past that costs capability, not configuration: **24.5 %** for
Focused with screen control kept, **31.3 %** for Focused (29.6 % against the
model server's measured 20,622-token baseline), and past that the tool schemas
are down to the ones the assistant genuinely uses. **Anything deeper needs the
agent runtime to change** — lazy tool loading (send a schema when a tool is
first wanted, not in every prefix) or compact schemas (the four largest are one
tool each, 5–6 KB apiece of prose and examples); skills-index compaction already
exists but is gated on `is_coding`, stranding ~1,700 tokens of headroom.

1.2.x follow-ups, in the order they pay:

1. **Lazy / on-demand tool schemas** in the agent runtime — the only change that
   scales past ~31 % without removing capability.
2. **Compact tool schemas** for the four 5–6 KB single-tool offenders
   (`session_search`, `delegate_task`, `computer_use`, plus `terminal`'s pair).
3. **Ungate skills-index compaction from `is_coding`** — ~1,700 tokens (~2.3 s)
   that is already implemented and simply unreachable from this surface.

All three belong upstream in `~/.hermes/hermes-agent`, not in a dashboard patch
of it.

## Recommendation

Switch this machine to **Balanced** in Settings › Agent & Models › Prompt
budget, and to **Focused** if the chat surface is what you actually use — it
saves ~6,600 tokens and ~8.8 s on every new conversation for screen control,
sub-agents and in-chat history search, each one click back on. New installs
default to Balanced through the first-run sheet.

## Context meter and compaction (2026-09-07 15:40)

The prompt-budget work above measures the FIXED prefix a new conversation pays.
This section is its other half: what a conversation costs once it is running,
and what the runtime does when it gets too big.

**Compression defaults on this machine** — `compression` in `~/.hermes/config.yaml`,
unchanged by this work (read at `agent/agent_init.py:1400-1448`):

| Key | Value | Runtime default | Meaning |
|---|---|---|---|
| `enabled` | `true` | `true` | compaction is on |
| `threshold` | `0.5` | `0.50` | compact at 0.5 x the window |
| `target_ratio` | `0.2` | `0.20` | summarise down to 0.2 x that threshold |
| `protect_last_n` | `20` | `20` | recent messages never summarised |
| `protect_first_n` | `3` | `3` | opening messages never summarised |

`model.context_length` is **65,536**, not the roster's native 262,144 for the
Qwen3.8 family — the compressor multiplies its threshold by hermes's configured
context length, so 65,536 is the only window a percentage can honestly be taken
against. That puts the compaction point at **32,768 tokens** and the summary
target at roughly **6,553**. No `auxiliary:` block exists, so the summariser
runs on the main model (`_resolve_task_provider_model` drops an unset/`auto`
model and falls back to the main runtime).

| 2:35 PM | 20,074 | 0 % | 24 s | no |
| 1:48 PM | 26,925 | 96 % | 2.2 s | no |

Folded into one turn, the 1:47-1:48 PM conversation reads:

```
GET /api/context/turn?since=1788803280&until=1788803333
  prompt_tokens 26,925   cached 25,882 (96.1 %)   new 1,043
  prefill 9.83 s across 5 requests   decode 32.7 tok/s   396 tokens out
  41.1 % of the 65,536 window        compacted: false
```

Three things fall out of that table, and all three are the argument for the
meter existing:

1. **The cache is the whole story.** A cold first turn pays 24-28 s of prefill
   for ~20.6k tokens (~750-830 tok/s). Every turn after it is 94-99 % cached and
   costs 1-3 s, at 8,000-24,000 tok/s. The chip says which of the two just
   happened, which is the only way to tell a slow model from a cold cache.
2. **Nothing on this machine has ever compacted.** The largest prompt in the
   whole 4.3 MB log is 31,856 tokens (2026-09-05), against a 32,768-token
   threshold — it came within 912 tokens and stopped. So compaction is untested
   here in practice, and the "Compacted" column is honest rather than decorative.
3. **The 30 %-drop heuristic needs a time guard.** Without one, the 11:49 AM
   turn (20,622 after 31,856) reads as a compaction; it is a new conversation two
   days later starting from the fixed prefix again. Requests more than ten
   minutes apart are now treated as different conversations
   (`_CX_SAME_CONVO_GAP_S`), which is what turned that row back to "no".

Raising `threshold` past ~0.49 would push the compaction point above the
31,856-token high-water mark and effectively never compact on this workload;
lowering it to 0.35 would put it at 22,938, i.e. inside the ordinary 1:48 PM
conversation. The card exists so that trade is made against this table rather
than against a feeling. **The owner's values were not changed.**

## Tool output budget — the variable half

The prompt budget above is the **fixed** cost: what a fresh conversation pays
before the first token. This section is the **variable** cost — what each tool
call adds to the transcript afterwards, and what it is capped at.

### Why a cap is needed at all

`model_tools.py` returns a tool's result string straight into
`make_tool_result_message`, so the result enters the conversation verbatim.
There is no global size check at that seam. Concretely, on this machine's
65,536-token window:

- one `read_file` at the agent's own 100,000-char ceiling is ~28,000 tokens,
  **42 % of the window**, in a single message;
- one `terminal` at its 50,000-char ceiling is ~14,000 tokens, **21 %**;
- `search_files`, `web_search`, `session_search`, `process`, `execute_code`,
  `memory` and every MCP or plugin tool have **no ceiling at all**.

And it is not paid once. Prefill is compute-bound at ~750 tok/s, and every
later turn in the same conversation re-prefills everything before it, so an
oversized result is charged again on every turn until compaction removes it.

### What the runtime already does (measured, not assumed)

| Tool | Cap | Shape | Config key |
|---|---|---|---|
| `terminal` | 50,000 chars | 40 % head / 60 % tail | `tool_output.max_bytes` (`tools/tool_output_limits.py`, `DEFAULT_MAX_BYTES`) |
| `read_file` | 100,000 chars | plus 2,000-line / 2,000-char-per-line pagination | `file_read_max_chars` (`tools/file_tools.py`, `_DEFAULT_MAX_READ_CHARS`) |
| `web_extract` | 15,000 chars | head+tail, full text stored on disk | `web.extract_char_limit` (`tools/web_tools.py`, `DEFAULT_EXTRACT_CHAR_LIMIT`) |
| everything else | — | — | — |

Three tools, three numbers, three keys, no shared idea of a budget, and each
number chosen for the tool rather than for the window. `web_extract` is the
one that already has the right *shape* — cap what the model sees, keep the
whole thing on disk — and that shape is what we generalised.

### The default, and why 24,000 chars

**24,000 characters ≈ 6,700 tokens ≈ 10 % of a 65,536-token window.**

The reasoning:

1. **A share of the window, not a size.** The number a user can reason about is
   "how much of my context may one tool call spend". Ten per cent means a turn
   can make several tool calls and still leave the majority of the window for
   the conversation. The card and the API therefore quote the percentage
   alongside the chars, computed from the live `model.context_length`, so the
   label stays honest on a machine configured differently.
2. **3.6 chars/token** is the ratio `aux_promptbudget.py` measured against the
   model server's own `prompt_tokens` lines. It is a prose-and-code ratio, so
   for tool output it is conservative if anything.
3. **Comparable harnesses land in the same place.** Codex CLI caps at 256 lines
   / 10 KiB head+tail; DeepSeek's `dsh` uses head/tail retention with
   spill-to-disk and a retrieval hint. 24k chars is deliberately more generous
   than Codex's 10 KiB, because a local 65k window with a spill file is a
   different trade than a hosted 200k one with no disk.
4. **It is above every useful whole result and below every runaway one.** A
   directory listing, a test summary, a diff, an API response: all comfortably
   under. A build log, a `find /`, a minified bundle: all over, and all things
   the model should page through rather than swallow.
5. **The floor of the configurable range, 4,000 chars, doubles as the fast
   path.** A result at or under 4,000 chars cannot exceed any legal budget, so
   the plugin returns it without reading the settings file or touching disk.
   The overwhelming majority of tool calls take that path.

The other three choices offered are 8k (3.4 %), 16k (6.8 %) and 48k (20.3 %);
the API accepts anything from 4,000 to 200,000.

### Design decisions worth recording

- **A plugin, not a dashboard feature.** The cap has to run where the tool
  result is produced, which is the agent's process — `hermes serve` for the hub
  and Telegram, `hermes -z` for briefings and the watchtower, and an
  interactive CLI. `transform_tool_result` is the one seam all of those share
  (`hermes_cli/plugins.py` `VALID_HOOKS`; fired in `model_tools.py` after
  `post_tool_call` and before the result is appended to context; a callback
  that returns a string replaces the result, first string wins, fail-open).
  Zero changes to `~/.hermes/hermes-agent`.
- **Truncated is not incomplete.** The marker says in words that the tool
  succeeded and that the text was trimmed to fit. Without that, a model reading
  an ellipsis concludes the command failed and runs it again — which is the
  loop the budget exists to prevent, made worse.
- **Nothing is lost.** The full original is written to
  `~/.hermes/dashboard/spill/<date>/<tool>-<8hex>.txt` (dir 0700, file 0600,
  swept at 7 days) and the marker names the path, so the model can `read_file`
  with an offset or `search_files` over it. Turning the spill off is allowed,
  and then the marker says the middle is genuinely gone.
- **Whole beats truncated.** A result that parses as JSON and fits after
  minification is returned whole. Head/tail'ing JSON produces something that
  parses as nothing.
- **Fail-open twice.** The runtime already wraps the hook dispatch; the plugin
  wraps every path of its own and returns `None` (leave the result alone) on
  any exception, on a non-string result, on a corrupt settings file, and on a
  failed spill.

## Memory layer v1 — the durable half (2026-09-07)

`docs/plans/harness-research.md` §5 "Memory layers" and §7 "1.2.2": the evidence
points at a **minimal, verifiable** design — durable facts with recency decay,
retrieved through the FTS5 index this repo already ships — and away from a
vector DB or an LLM-extraction pipeline, which are validated only against
frontier cloud models and would compete for the same GPU budget as the turn
they are meant to help. That is what shipped.

### What was verified before building

- **The agent's own memory is a frozen per-session snapshot.**
  `~/.hermes/hermes-agent/tools/memory_tool.py` `MemoryStore` reads `MEMORY.md`
  (2,200 chars) and `USER.md` (1,375 chars) into `_system_prompt_snapshot` at
  `load_from_disk()` and `format_for_system_prompt()` serves that snapshot, not
  live state, for the whole session — rebuilt only after a compression event.
  So it cannot answer "what is relevant to *this* message", and anything
  imported from those two files must be flagged and never injected a second
  time.
- **`access_preamble()` is the right seam.** It already appends `[context]`
  lines to the outbound prompt text per turn, and its own comment records the
  measured ordering rule (`b3-prefix-ttft-findings.md`): stable lines first,
  volatile last, because the mlx prompt cache reuses the longest common token
  prefix. The memory block therefore goes **after** grants/invariants/index/
  tasks/calendar and **before** the wall-clock line.
- **`server.py` `read_memory()` was wrong** — it split `USER.md` on `\n`
  instead of the `\n§\n` entry delimiter, so on this machine it reported three
  "facts" for two real entries, the third being the bare `§` separator. Fixed
  in place; a hand-written entry that is nothing but markdown bullets still
  yields one fact per bullet, which is the one shape the old reader got right.
- **There is nothing personal in onboarding.** `aux_onboarding.py`
  `_onb_prefs()` returns idle minutes, prewarm, quiet hours and the prompt-budget
  profile — a machine and service profile, no name, role or goals. It is
  therefore **not** a fact source, and no importer was written for it.

### The shape

`dashboard/aux_memlayer.py`, store at `~/.hermes/dashboard/memory.db` (0600,
WAL sidecars chmod'ed too). Facts are ranked `BM25(text vs the message) ×
0.5^(days_since_last_used / 30) × weight`; pinned facts are candidates whether
or not they match; archived facts and `in_snapshot` facts are excluded in SQL.
The rendered block is ordered **stable → volatile**: pinned first, then the
rest oldest-updated first, most-recent last, then up to two episodic lines —
so the same set of facts always renders the same bytes.

Episodic lines match conversation **titles only**, not transcript bodies. The
first cut matched either, and "who is jane and does she know anyone in the nyc
ai scene" came back with a conversation about Shortcuts, matched on
*does* / *the* / *in*. Function words are now dropped before the query is
built, and the match is restricted to the column the rendered line actually
shows — a title hit means that conversation was *about* this.

### Measured injected size

Live, through `GET /api/memory/preview?text=`, against this machine's real
store (2 injectable facts — the You-Model files are still just their templates,
so there is very little to retrieve yet). Budget 600 chars:

| Message | Chars | Tokens | Facts | Episodic |
|---|---|---|---|---|
| "who is jane and does she know anyone in the nyc ai scene" | 40 | 11 | 1 | 0 |
| "explain matrix multiplication again like you did before" | 107 | 30 | 0 | 2 |
| "what should I work on today" | 0 | 0 | 0 | 0 |

Against a **synthetic 10-fact store** (a throwaway `HOME`, so the real store was
untouched), with a message deliberately built to match most of it — "remind me
about hermes, the model, the dashboard and emran's scholarship email":

| Budget | Chars | Tokens | Facts |
|---|---|---|---|
| 300 | 243 | 68 | 3 |
| 600 | 597 | 166 | 7 |
| 1,200 | 789 | 219 | 9 |

So the 600-char default is ~166 tokens at saturation — **0.25 % of the 65,536
window, and about 0.8 % of the ~20.5k fixed prefix measured at the top of this
document**. At 750 tok/s prefill that is roughly 0.2 s per turn, worst case.

The third row of the first table is the honest limitation: "what should I work
on today" retrieves nothing, because lexical retrieval needs lexical overlap
and no stored fact contains *work* or *today*. That is the cost of not running
an embedding model, and it was taken deliberately (§5: if semantic retrieval is
ever added, use a small dedicated embedding model, never the 27B).

### Proof the off switch is free

With `memory_layer.enabled = false`, `memlayer_lines()` returns `""` before
touching the store, so nothing is appended and `job["memory_chars"]` is never
set. Verified by building `access_preamble()` three ways against the same
inputs — module absent, module present and off, module present and on:

```
module absent       :  1452 chars
module present, OFF :  1452 chars   <- byte-identical
module present, ON  :  1552 chars   (+100, one [memory] line, inserted
                                     after the tasks line and before
                                     "[context] Local time: …")
```

### Left for later

No model has ever been asked to summarise, extract or consolidate anything —
there is no write-back path from a conversation into the store, so facts are
added by the owner or imported from files they already wrote. Whether facts
retrieved this way actually reduce full-history replay in practice (§7's
"Measure") needs turns on a real model and is not answered here.
