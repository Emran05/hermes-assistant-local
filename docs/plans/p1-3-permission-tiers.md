# Graduated Permission Tiers — design spec (P1)

Workstream P1.3 (DEVPLAN Phase 1 #3). Moves the dashboard's approval path from
binary manual-approve-everything to per-action-class trust tiers: **AUTO** (run
silently), **ASK** (surface to the user, as today), **NEVER** (auto-deny with a
reason). We sit *in front of* hermes-agent's own `approvals.mode: manual` —
hermes keeps asking; our policy layer answers on the user's behalf when, and
only when, the user has pre-decided.

Everything below is grounded in the pinned checkout
`~/.hermes/hermes-agent` (v0.18.x) and the current
`dashboard/server.py` / `dashboard/hermes_rpc.py` as of 2026-07-05.

---

## 0. The two questions this spec must answer

### Q1 — What is the canonical tool taxonomy?

**Ground truth first.** In hermes-agent v0.18, `approval.request` events are
generated by exactly three sources (verified in
`~/.hermes/hermes-agent/tools/`):

1. **`terminal_tool.py`** → `check_all_command_guards()` — shell commands
   matching one of the **73 `DANGEROUS_PATTERNS`** entries
   (`tools/approval.py` lines 498–712). The `pattern_key` sent in the event
   payload **is the human-readable description string** of the matched pattern
   (`approval.py:1347: pattern_key = description`), e.g. `"recursive delete"`,
   `"git force push (rewrites remote history)"`.
2. **`code_execution_tool.py`** → `check_execute_code_guard()` — whole
   `execute_code` scripts. `pattern_key` is the literal string
   `"execute_code"` (`approval.py:2630`).
3. **`mcp_tool.py`** → `request_elicitation_consent()` — MCP elicitation
   consent. `pattern_key` is the literal string `"mcp_elicitation"`
   (`approval.py:2852`).

Additionally, **12 `HARDLINE_PATTERNS`** (rm -rf /, mkfs, dd to block device,
fork bomb, shutdown…) are blocked by hermes *before* any approval request is
emitted — they can never reach our policy layer, which is exactly right: the
catastrophic floor stays upstream and unconditional.

So the canonical taxonomy is **not** "tools" (read_file, computer_use, gmail…)
— those never emit approval requests today. It is an **action-class taxonomy
over hermes pattern keys**, with reserved class slots for future tool classes
(Shortcuts action-bus, computer-use, send-message) so Phase 3 plugs into the
same table. The 17 canonical classes:

| class id | risk | default tier | floor | example member pattern_keys |
|---|---|---|---|---|
| `read-only` | low | `auto` | — | *(reserved — no hermes patterns today; future read-only bus tools)* |
| `git-destructive` | med | `ask` | — | `git reset --hard (destroys uncommitted changes)`, `git force push (rewrites remote history)`, `git force push short flag (rewrites remote history)`, `git branch force delete`, `git branch force delete (long flags)`, `git branch force delete (long flags, force-first)`, `git clean with force (deletes untracked files)` |
| `file-perms` | med | `ask` | — | `world/other-writable permissions`, `recursive world/other-writable (long flag)`, `recursive chown to root`, `recursive chown to root (long flag)` |
| `project-config` | med | `ask` | — | `overwrite project env/config via tee`, `overwrite project env/config via redirection`, `overwrite project env/config file` |
| `process-control` | med | `ask` | — | `stop/restart system service`, `kill all processes`, `force kill processes`, `force kill processes (killall -KILL)`, `force kill processes (killall -s KILL)`, `kill processes by regex (killall -r)` |
| `container-lifecycle` | med | `ask` | — | `docker compose restart/stop/kill/down (container lifecycle)`, `docker restart/stop/kill (container lifecycle)` |
| `mcp-consent` | med | `ask` | ask | `mcp_elicitation` |
| `destructive-delete` | high | `ask` | ask | `delete in root path`, `recursive delete`, `recursive delete (long flag)`, `Windows cmd destructive delete`, `Windows PowerShell destructive delete`, `xargs with rm`, `find -exec/-execdir rm`, `find -delete` |

| `hermes-self` | critical | `ask` | ask | `stop/restart hermes gateway (kills running agents)`, `hermes update (restarts gateway, kills running agents)`, `start gateway outside systemd (use 'systemctl --user restart hermes-gateway')`, `kill hermes/gateway process (self-termination)`, `kill process via pgrep/pidof expansion (self-termination)`, `kill process via backtick pgrep/pidof expansion (self-termination)`, `stop/restart hermes launchd service (kills running agents)`, `in-place edit of Hermes config/env`, `in-place edit of Hermes config/env (long flag)`, `in-place edit of Hermes config/env (perl/ruby)` |
| `credential-write` | critical | `never` | ask | `copy/move file into sensitive credential/SSH/shell-rc path`, `in-place edit of sensitive credential/SSH/shell-rc path`, `in-place edit of sensitive credential/SSH/shell-rc path (long flag)`, `in-place edit of sensitive credential/SSH/shell-rc path (perl/ruby)` |
| `disk-device` | critical | `never` | ask | `format filesystem`, `disk copy`, `write to block device` |
| `privilege-escalation` | critical | `never` | ask | `sudo with privilege flag (stdin/askpass/shell/list)`, `sudo with combined-flag privilege escalation` |
| `unknown` | high | `ask` | ask | *(any pattern_key not in the table — new upstream patterns land here automatically)* |

**Floor** = the least-restrictive tier the class may ever be set to. Classes
with floor `ask` can never be `auto` — enforced at both write time (API
rejects) and read time (resolver clamps). Only `read-only`, `git-destructive`,
`file-perms`, `project-config`, `process-control`, and `container-lifecycle`
may ever be AUTO. `hermes-self` is floor-`ask` (not default-never) because
`hermes config set` flows are sometimes legitimately user-initiated — but
`~/.hermes/config.yaml` *is* the security policy (approval.py:213 comment), so
it can never be auto.

The full 73-key → class table ships as `PATTERN_CLASS` in
`dashboard/permissions.py`. The build step regenerates the key list from the
pinned checkout with:

```bash
sed -n '498,712p' ~/.hermes/hermes-agent/tools/approval.py | grep -o '"[^"]*"),' | sort -u
```

and must map **every** extracted key; keys added by future upstream bumps fall
into `unknown` (→ ask) automatically, so an upgrade can loosen nothing.

### Q2 — How do we map an incoming `approval.request` to a policy entry?

The event payload (built at `approval.py:2462` for terminal, `:2754` for
execute_code, `:2849` for elicitation, redacted via
`redact_sensitive_text`, emitted by `tui_gateway/server.py:_emit_approval_request`
with `command` re-redacted) is:

```json
{
  "command":        "rm -rf ~/scratch/build",
  "pattern_key":    "recursive delete",
  "pattern_keys":   ["recursive delete"],
  "description":    "recursive delete",
  "allow_permanent": true
}
```

(`allow_permanent` present only on the terminal path; elicitation payloads put
the consent message in `command`.)

**Resolution algorithm** (`permissions.decide(payload)` — deterministic, no
LLM, total function, never raises):

1. `keys = payload.get("pattern_keys") or [payload.get("pattern_key") or ""]`;
   drop non-string entries. If empty → class `unknown`, tier `ask`, done.
2. For each key, resolve a tier:
   a. **Pattern override**: `policy["patterns"][key]` if present and valid.
   b. Else **class tier**: `policy["classes"][PATTERN_CLASS[key]]`.
   c. Else (key not in `PATTERN_CLASS`) **heuristic fallback** on the key
      text: contains `credential`/`SSH`/`shell-rc` → `credential-write`;
      `hermes`/`gateway` → `hermes-self`; `sudo` → `privilege-escalation`;
      `delete`/`rm ` → `destructive-delete`; `block device`/`filesystem` →
      `disk-device`; else `unknown`. Then use that class's tier.
3. **Most-restrictive wins** across all keys: `never(2) > ask(1) > auto(0)`.
4. **Floor clamp**: if any resolved class has floor `ask` and the result is
   `auto`, clamp to `ask` (belt-and-braces vs. a hand-edited policy file).
5. **Trust clamp**: if the policy file fails its integrity check (§2 sidecar)
   or is malformed, all `auto` results clamp to `ask` (`never` still honored
   from the last-known-good parse, else everything is `ask`).
6. Return
   `{"tier","class","classes":[…],"pattern_key",<br>"reason": "recursive delete → destructive-delete is set to Ask", "clamped": bool}`.

**Response mapping** (interop with `approvals.mode: manual`): valid
`approval.respond` choices upstream are `once | session | always | deny`
(anything not `deny` approves; `session`/`always` also persist to hermes's own
allowlists — `approval.py:2515-2524`, `tui_gateway/server.py:9770`). Our layer
sends **only** `"once"` (AUTO) or `"deny"` (NEVER) — never `session`/`always` —
so hermes's session/permanent allowlists **never grow** and
`~/.hermes/permissions.json` remains the single, visible source of graduated
trust. The existing UI "Approve" button's `"approve"` choice also lands as
approve-once upstream (non-deny, no persistence branch) and stays as-is.

## Goal & acceptance criteria

Done means:

1. `~/.hermes/permissions.json` exists with the 17-class schema below;
   deleting it, truncating it, or filling it with garbage never breaks a chat
   turn — the engine falls back to defaults with `auto` disabled (fail-safe to
   ASK).
2. A pattern whose class is **AUTO** (e.g. `git-destructive` set to auto, then
   `git reset --hard` in a scratch repo via hub chat) completes with **no
   approval card**, a transient "auto-approved" status line, and an audit-log
   entry — and hermes's permanent allowlist
   (`~/.hermes/config.yaml` `command_allowlist`) is **unchanged** afterward.
3. A pattern whose class is **NEVER** is auto-denied: the agent receives the
   upstream BLOCKED message, the chat shows "Blocked by policy: …", an
   audit-log entry exists, and the turn ends normally (no hang, no retry).
4. A pattern whose class is **ASK** behaves byte-for-byte like today's manual
   flow (approval card, Approve/Deny buttons), plus a tier/class line on the
   card and an audit entry recording the user's choice.
5. The Trust panel in Mind lists all 17 classes with risk labels and a
   3-state segmented control; floor-locked AUTO segments are visibly disabled;
   changes persist across dashboard restart and take effect on the very next
   approval without any service restart.
6. `POST /api/permissions` refuses (HTTP 403, `{"ok":false,"error":…}`) any
   attempt to set a floor-`ask` class to `auto`, and refuses unknown
   classes/tiers (400).
7. Out-of-band edits to `permissions.json` (e.g. by the agent itself) are
   detected via the integrity sidecar: the engine clamps all AUTO→ASK and the
   Trust panel shows a "policy changed outside the dashboard" banner until the
   user clicks **Review & re-trust**.
8. `python3 -m py_compile` passes on all three touched/new Python files;
   `node --check dashboard/trust.js` passes; the headless render harness
   renders the Trust panel from canned JSON without throwing.

## Data model

### 1. Policy store — `~/.hermes/permissions.json` (mode 600)

```json
{
  "version": 1,
  "updated": 1751673600.0,
  "updated_by": "dashboard",
  "classes": {
    "read-only": "auto",
    "git-destructive": "ask",
    "file-perms": "ask",
    "project-config": "ask",
    "process-control": "ask",
    "container-lifecycle": "ask",
    "mcp-consent": "ask",
    "destructive-delete": "ask",
    "sql-destructive": "ask",
    "arbitrary-exec": "ask",
    "execute-code": "ask",
    "system-config": "ask",
    "hermes-self": "ask",
    "credential-write": "never",
    "disk-device": "never",
    "privilege-escalation": "never",
    "unknown": "ask"
  },
  "patterns": {
    "git force push (rewrites remote history)": "never"
  }
}
```

- `classes`: class-id → `"auto"|"ask"|"never"`. Missing/invalid entries take
  the class default from `CLASS_META` (the table in §Q1).
- `patterns`: optional per-`pattern_key` overrides (exact hermes description
  strings). Precedence: pattern > class > default. Overrides obey the same
  floor as their class.
- Written atomically (`tmp` + `os.replace`), like `write_json()`
  (server.py:78).

### 2. Integrity sidecar — `~/.hermes/dashboard/permissions.sha` (mode 600)

One line: `sha256(canonical policy bytes)`. Written on every dashboard-side
save and on **Review & re-trust**. On load, hash mismatch ⇒ "untrusted"
mode (§Q2 step 5). This is tamper *detection*, not prevention (same-user
writes can't be prevented) — but detection + fail-safe clamp closes the
prompt-injection escalation "agent edits permissions.json then acts": the
edit itself disables AUTO until a human re-trusts.

### 3. Audit log — `~/.hermes/dashboard/permissions-log.jsonl` (append-only)

One JSON object per line:

```json
{"ts": 1751673601.2, "job": "9f2c1a7b3d4e", "session": "s_ab12cd",
 "pattern_key": "recursive delete", "class": "destructive-delete",
 "tier": "ask", "action": "asked", "choice": "deny",
 "command": "rm -rf ~/scratch/build"}
```

`action` ∈ `auto-approved | auto-denied | asked | policy-error`;
`choice` (only when `action=asked`, appended as a second entry
`action:"user-approve"|"user-deny"` when the user clicks). `command`
truncated to 2000 chars (execute_code scripts can be huge). Rotation: when
size > 1 MB at append time, rename to `permissions-log.jsonl.1` (single
generation kept).

### 4. In-code tables (in `dashboard/permissions.py`)

```python
TIERS = ("auto", "ask", "never")
CLASS_META = {  # id -> {label, risk, default, floor, desc}
    "credential-write": {"label": "Credential & SSH writes", "risk": "critical",
                          "default": "never", "floor": "ask",
                          "desc": "Writes to SSH keys, credential files, shell rc files."},
    # ... all 17, exactly per the table in Q1 ...
}
PATTERN_CLASS = {  # all 73 dangerous-pattern description keys + 2 literals
    "recursive delete": "destructive-delete",
    "execute_code": "execute-code",
    "mcp_elicitation": "mcp-consent",
    # ... complete ...
}
```

## Backend

### New module: `dashboard/permissions.py` (NEW file, ~250 lines)

**A real sibling import, not an exec-include — with justification.** The
enforcement point lives in `hermes_rpc.py`, which is itself a normal module
imported by server.py (server.py:866 `import hermes_rpc`), so the policy
engine must be importable anyway; exec-including the same source into
server.py's globals would create a *second* engine instance with its own lock.
A single `import permissions` from both hermes_rpc.py and the route hooks
keeps one instance (one `sys.modules` entry, one lock, one mtime cache) and
still honors the exec-include rule's *intent*: zero surgery on the 2400-line
server.py beyond tiny route-dispatch hooks (below). `permissions.py` is fully
self-contained: `import hashlib, json, os, threading, time` only — no
server.py helpers.

Public surface:

```python
def decide(payload: dict) -> dict            # §Q2 algorithm; never raises
def audit(job: dict, payload: dict, verdict: dict, action: str, choice: str = "") -> None
def permissions_payload() -> dict            # GET /api/permissions
def permissions_set(body: dict) -> dict      # POST /api/permissions (raises nothing; returns ok/err + _status)
def permissions_log(n: int = 50) -> dict     # GET /api/permissions/log
def permissions_test(pattern_key: str, command: str = "") -> dict  # GET /api/permissions/test
```

Internals: `_load()` re-reads `~/.hermes/permissions.json` only when mtime
changes (per-call `os.stat`, cached parse behind `_lock = threading.Lock()`);
`_save(policy)` = atomic write + sidecar rewrite + mtime-cache bust;
`_trusted()` compares sha256 against the sidecar; `_resolve(keys)` implements
steps 2–5.

### Endpoints

**`GET /api/permissions`** → 200

```json
{"ok": true, "trusted": true, "path": "/Users/emrannasseri/.hermes/permissions.json",
 "exists": true,
 "classes": [
   {"id": "destructive-delete", "label": "Destructive deletes", "risk": "high",
    "tier": "ask", "default": "ask", "floor": "ask", "auto_allowed": false,
    "desc": "rm -r, find -delete, xargs rm…", "pattern_count": 8,
    "recent": {"auto-approved": 0, "auto-denied": 0, "asked": 3}},
   ...17 total, ordered critical→low...
 ],
 "patterns": {"git force push (rewrites remote history)": "never"},
 "recent": [ ...last 20 audit entries, newest first... ]}
```

Error cases: none fatal — missing file ⇒ `exists:false`, defaults shown;
malformed file ⇒ `ok:true, trusted:false, policy_error:"…"`.

**`POST /api/permissions`** — body is one of:

| body | effect | responses |
|---|---|---|
| `{"op":"set_class","class":"git-destructive","tier":"auto"}` | set class tier | 200 `{"ok":true,"classes":[…]}` · 400 unknown class/tier · 403 `{"ok":false,"error":"'credential-write' has a safety floor of 'ask' and cannot be set to 'auto'"}` |
| `{"op":"set_pattern","pattern":"<exact key>","tier":"never"}` | per-pattern override | 200 / 400 unknown tier or empty pattern / 403 floor (pattern's class floor applies) |
| `{"op":"clear_pattern","pattern":"<exact key>"}` | remove override | 200 (idempotent) |
| `{"op":"reset"}` | restore all defaults, clear overrides | 200 |
| `{"op":"retrust"}` | rewrite sidecar for current file content | 200 `{"ok":true,"trusted":true}` |
| anything else | — | 400 `{"ok":false,"error":"unknown op"}` |

All successful writes append an audit entry `action:"policy-change"` with the
op echoed, and bump `updated`/`updated_by:"dashboard"`.

**`GET /api/permissions/log?n=50`** → `{"ok":true,"entries":[…]}` (n clamped
to 1..500; missing log file ⇒ empty list).

**`GET /api/permissions/test?pattern_key=recursive%20delete&command=rm%20-rf%20x`**
→ `{"ok":true,"verdict":{...decide() output...}}` — dry-run for tests and the
UI's "what would happen" affordance. Never mutates state.

## Edge cases & failure modes

- **`permissions.json` missing** → defaults, `exists:false`; first POST
  creates it 600 + sidecar. No behavior change vs. today (all high classes
  ask).
- **Malformed JSON / wrong types** (`"classes": []`, tier `"yolo"`, file is a
  directory) → `_load()` catches everything, returns defaults with
  `trusted:false`; decide() clamps auto→ask; GET carries `policy_error`.
- **Sidecar missing but policy present** (first run after upgrade, or agent
  deleted it) → untrusted mode (fail-safe), banner prompts re-trust once.
- **Agent edits the policy file mid-session** → next `decide()` stat-detects
  mtime change, rehash fails vs sidecar → auto suspended that same call.
  TOCTOU window is one `decide()` invocation, and the *worst case* inside it
  is a stale *stricter* read (mtime cache only serves last-parsed content).
- **Concurrent POSTs / decide() during POST** → single process, one
  `threading.Lock` around load/save; atomic `os.replace` means readers never
  see partial JSON.
- **Two approvals queued in one turn (multi-command)** → handled per event in
  arrival order; FIFO `resolve_gateway_approval` keeps responses aligned (see
  ordering note above). A mixed AUTO-then-ASK sequence auto-answers #1 and
  surfaces #2.
- **`approval.respond` WSError on AUTO** → fail open to ASK (card surfaces;
  user decides). On NEVER → also surface (user can deny by hand; policy
  wanted deny, and denying is still one click). Never silently dropped —
  DEVPLAN metric "zero approvals silently dropped".
- **User never responds to ASK** → upstream `gateway_timeout` (300s,
  approval.py:2150) fires: hermes returns BLOCKED("Silence is not consent"),
  turn completes; our `done` handling already clears the card
  (index.html:2021).
- **Huge `command`** (multi-KB execute_code script) → audit truncates to
  2000 chars; UI `code` block already scrolls (`.approval code` styles);
  payload itself passes through untouched.
- **Log growth** → 1 MB rotate check on every append; append uses
  `open(...,"a")` single-`write()` lines (atomic enough for one process on
  APFS).
- **Serve down → `hermes -z` fallback path** (server.py:909) →
  non-interactive, approval-needing actions fail closed upstream
  (CLAUDE.md gotcha); policy engine simply never consulted. Correct: nothing
  runs un-asked.
- **Model paused / offline** → no turns, no approvals; Trust panel is pure
  file I/O and keeps working.
- **Telegram/CLI surfaces** → NOT covered: those sessions register their own
  notify callbacks in the gateway process; our layer only fronts dashboard
  serve sessions. Hermes's manual mode + hardline floor still protect them
  unchanged. (Documented in panel footnote; see Open questions.)
- **Upstream pattern renames on a hermes-agent bump** → renamed keys fall to
  `unknown` → ask. Tier can only get *stricter* from drift, never looser.
- **`mcp_elicitation` AUTO nonsense** → `mcp-consent` floor is ask; an
  elicitation is a question, auto-"approving" it would silently answer
  "accept". Floor makes this unrepresentable.
- **User sets every class to never** → agent becomes effectively read-only;
  panel shows a passive hint ("Most actions are blocked — Hermes will refuse
  many requests") but does not resist: that's a legitimate posture.
- **USER.md.lock-style stale locks** — N/A: no lock files used; single
  process + in-process lock + atomic replace.

## Security & safety

- **Fail-safe bias**: every failure mode (missing file, parse error, unknown
  key, tamper detection, respond error) degrades toward ASK — never toward
  AUTO. `never` is honored from last-known-good state even when untrusted.
- **Safety invariants untouched**: no send capability added anywhere; Gmail
  remains read+draft (nonexistent yet); Telegram lock is upstream config; all
  policy evaluation is local, deterministic, zero-inference (explicitly *not*
  hermes's `smart` LLM approval — a policy that can be prompt-injected is not
  a policy). No user secrets handled: payloads arrive pre-redacted
  (`redact_sensitive_text` upstream), and we store only the redacted text.
- **Hermes's floor stays beneath us**: HARDLINE_PATTERNS block before any
  event fires; our layer can only decide things hermes was already willing to
  ask about. We never send `session`/`always`, never write
  `command_allowlist`, never touch `~/.hermes/config.yaml`, never change
  `approvals.mode`. Removing our layer reverts the system to today's exact
  behavior.
- **Escalation resistance**: the known escalation path (approval.py:32
  comment — an allowlist file edit bypasses checks) is mitigated for *our*
  store by the sidecar-hash untrusted clamp (§Data model 2): an agent-authored
  edit to permissions.json disables AUTO until a human re-trusts in the UI.
  Floors are additionally enforced at read time so even a hand-crafted
  `"credential-write":"auto"` line resolves as ask.
- **Must refuse**: `set_class`/`set_pattern` below floor (403); unknown
  class ids and tiers (400); any op when body is not a JSON object (400).
  The UI never offers a floor-violating state (disabled segment), but the
  server is the enforcement point, not the UI.

## Open questions / risks

1. **Telegram-surface enforcement.** Our layer fronts only dashboard serve
   sessions. To govern Telegram/CLI approvals with the same file, the right
   seam is upstream's `pre_approval_request` plugin hook
   (hermes_cli/plugins.py:186) — a small hermes plugin reading
   `~/.hermes/permissions.json`. Deferred: touching the gateway process is
   Phase-2+ risk, and hermes manual mode still protects those surfaces today.
2. **execute_code granularity.** The whole-script guard uses one opaque
   `pattern_key="execute_code"`; inner `terminal()` calls made *by* the script
   re-enter the command guards independently (approval.py:2704 comment), so
   per-command policy still applies beneath the script-level ASK. Verify this
   double-gating empirically during test #4 and document.
3. **Payload field drift on upstream bumps.** `pattern_keys`/`allow_permanent`
   shapes are v0.18.x observations; the phase-boundary upgrade checklist must
   re-run `sed -n '498,712p' … | grep -o` extraction + one ASK drill. Drift
   fails safe (unknown → ask) but silently degrades AUTO usefulness.
4. **"Remember once" tier (DEVPLAN's `remember`).** Deliberately cut from v1:
   hermes already implements confirm-once-per-session upstream via the
   `session` choice, but using it would fork trust state into a second,
   invisible store. If wanted later: a `remember` tier that writes a
   session-scoped entry into *our* store (visible, expiring) — never
   upstream's.
5. **Risk-label copy.** "critical/high/med/low" chips need a wording pass with
   the user — labels are the product here (trust is the moat); wrong copy
   reads as either scary or lax.
6. **Sidecar UX friction.** Every legitimate hand-edit of permissions.json
   (config-as-code workflows, P1.6) trips the untrusted banner. Acceptable —
   one click to re-trust — but P1.6's docs must mention it.
