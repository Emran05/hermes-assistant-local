# Three installed harnesses vs. Hermes Assistant — what to port

Read first: `~/HermesAssistant/docs/plans/harness-research.md`, `~/HermesAssistant/docs/plans/1.2-baseline.md`.
Already adopted in Hermes 1.2.x (excluded from recommendations below): prompt-budget toolset profiles, tool-output budget with head/tail + spill-to-disk (ported from `dsh-output-retention`/`dsh-spill`), context meter + compression controls, memory layer v1, evals with history, JSONL/OTLP traces, doctor.

## Coverage
Sources read: dsh installed CLI (`~/.nvm/.../@deepseek-ai/dsh` rc.7, ~65 nested `@deepseek-ai/dsh-*` packages incl. sandbox/permissions/subagent/goal/plan-mode/invariants READMEs), dsh spike (`~/.hermes/dsh`, ~180 packages, incl. UI/client packages not shipped in rc.7's CLI shell), GitHub API for deepseek-ai/deepseek-harness, ECC plugin tree (`~/.claude/plugins/marketplaces/ecc`: hooks, agents, skills, commands, workflows, manifest), GitHub API for affaan-m/ECC, prime-agent README/package.json + GitHub API for PrimeIntellect-ai/prime-agent, one web search corroborating dsh's star-growth trajectory. All three repos' star/velocity data pulled directly from the GitHub REST API (self-reported by GitHub, not the vendors — treated as ground truth for star counts, but growth narrative from a Substack/blog source is secondary).

**dsh is the one "blowing up."** It has fewer total stars than ECC but was created less than a month ago and already has 85% of ECC's star count; independent reporting (Flowtivity, Pasquale Pillitteri) describes it setting a GitHub fastest-star-growth record (100k in 2 days). ECC has more stars in absolute terms but at roughly 1/8th the daily rate; it is a mature, steadily-growing project, not this month's surge. prime-agent is comparatively niche and not surging.

Caveat: star counts are a vanity/marketing-adjacent metric (self-reported by GitHub, not vetted for bot inflation); the "fastest star-growth record" claim is from third-party blogs, not DeepSeek itself, and should be read as directional not verified fact.

## 1. DeepSeek Harness (dsh) — feature inventory

dsh is architected as ~65-180 tiny npm packages composed via a Cordis DI/plugin kernel, split Service-Definition / Service-Provider / Consumer per capability ("everything is a plugin"). The **spike** (`~/.hermes/dsh`, ~180 packages) is a superset of the **installed rc.7 CLI** (`~/.nvm/.../@deepseek-ai/dsh`, ~65 direct + nested deps) — the rc.7 CLI ships all the same capability packages nested one level under its own `node_modules/@deepseek-ai/`, it's just missing the full client-UI package family (`dsh-client-ui-*`, ~40 packages: sidebar, workspace, trajectory viewer, permission-preset picker, plan viewer, subagent viewer, jobs UI, theme, directory pickers) and a few dev/testing packages (`dsh-loader-smoke`, `dsh-llm-mock-server`). Functionally the two are the same harness; the spike additionally has a browser-based UI layer that rc.7's headless/CLI-focused shell doesn't bundle by default.

| Feature | What it does | Hermes has it? | Portable how | Effort | Value |
|---|---|---|---|---|---|
| Permission presets (`dsh-permission-presets`) | Named bundles of `sandbox mode + approval policy` (`workspace-write`+`ask`, `danger-full-access`+`never`); one selector sets both knobs atomically, logged as an event | No — Hermes has ad hoc per-tool checks, no unified named preset | Hermes plugin/config: a `permission_presets.yaml` + a dashboard toggle that sets sandbox+approval together | S | H |

### dsh — top 5 ports (ranked)
1. **Permission presets** — one named toggle sets sandbox mode + approval policy together, logged as an event. Mechanism: port `dsh-permission-presets`' `set(session, name)` pattern. Lands in: a new `permission_presets.py` used by the dashboard settings page and by `pre_llm_call`/tool-gate hooks. Effort S, value H.
2. **Shared sandbox-mode contract** — one `SandboxMode` enum (`read-only`/`workspace-write`/`danger-full-access`) resolved once per call and consumed by every tool wrapper (bash, fs, web), fail-closed on unavailability. Mechanism: port `dsh-sandbox`/`dsh-sandbox-policy`'s Service-Definition/Policy split. Lands in: a new `sandbox_policy.py` imported by the existing tool-execution layer in the hermes-agent runtime plugin hooks. Effort M, value H.
3. **Auditable one-shot approval service** — `approval.request()` returning `allowed-once`/`rejected`/`cancelled`/`unavailable`, fail-closed, logged as paired asked/decided events into the Flight Recorder. Mechanism: port `dsh-user-approval`'s seam. Lands in: `p1-3-permission-tiers.md`'s permission-tier implementation file (already tracked as a plan — this generalizes it into a reusable service other tools can call). Effort M, value H.
4. **`todo_write` tool + `ask_user_question` structured tool** — cheap, immediately useful model-facing tools; `todo_write` gives the model a durable, replace-wholesale task list logged to the session; `ask_user_question` gives a structured multi-choice clarification schema over the existing Telegram ask path. Mechanism: two small new tool definitions. Lands in: Hermes's tool registry module + a skill file documenting usage. Effort S, value M.
5. **Runtime invariants registry** — every Hermes subsystem (dashboard, gateway, memory layer, doctor) registers a self-check function into one central registry; `doctor` runs them all. Mechanism: port `dsh-invariants`' config (`enabled`, `package_allowlist`/`blocklist`). Lands in: extends the existing `doctor` command with a pluggable invariant list. Effort S, value M.

## 2. ECC (Claude Code plugin, "agent harness performance optimization system") — feature inventory

Structure: 285 skills, ~65 agents (mostly per-language build-resolvers/reviewers — Claude-Code-specific, not portable), a small number of slash commands (~90+, many CI/build/epic-workflow related), one `hooks/hooks.json` (PreToolUse/PostToolUse/Stop/SessionStart/SessionEnd/PreCompact hook graph — Claude-Code-specific event model), and one workflow (`orch-review.workflow.js`). Most of the 65 agents and most of the 285 skills are language/framework-specific (react-reviewer, django-build-resolver, flutter-review, cpp-build, etc.) and are not relevant to a Python-stdlib personal-agent product; they are Claude-Code-plugin scaffolding, not general harness ideas.

| Feature | What it does | Hermes has it? | Portable how | Effort | Value |
|---|---|---|---|---|---|
| `silent-failure-hunter` agent | Static review pass hunting empty catch blocks, dangerous fallbacks (`.catch(() => [])`), swallowed errors, missing timeouts/rollbacks | No — no equivalent review skill in Hermes | Hermes skill file: adapt the checklist (empty except blocks, `except: pass`, bare `return None` fallbacks, missing timeouts) into a Python-flavored `SKILL.md` for a code-review pass over Hermes's own dashboard/plugin code | S | M |
| `verification-loop` skill | Multi-phase gate before claiming work complete: build → typecheck → lint → tests+coverage → security grep (secrets, `console.log`) → diff review | Partial — Hermes has evals/doctor but not this exact pre-completion checklist | skill file: adapt phases to Python stack (pytest, ruff/mypy, grep for secrets/print-debugging) as a Hermes skill invoked before marking a task done | S | M |
| `code-reviewer`/`security-reviewer`/`typescript-reviewer` agents | Structured per-domain review checklists (Claude-Code subagents with `tools:` restriction and a "Prompt Defense Baseline" preamble against prompt injection) | Partial (Hermes has Claude escalation but no structured review-agent checklist) | The **prompt-defense-baseline preamble pattern** (treat fetched/tool content as untrusted, refuse role-override, reject unicode/homoglyph tricks) is the portable idea — bake it into Hermes's `transform_tool_result` hook so any tool output pattern-matched as instruction-injection gets flagged before reaching the model | M | H |
| Hooks system (`hooks.json`: PreToolUse/PostToolUse/Stop/SessionStart/SessionEnd/PreCompact) | Event-driven pre/post tool automations, block-on-exit-2 semantics, session lifecycle hooks | Yes, conceptually — Hermes already has `pre_llm_call`/`transform_tool_result` plugin hooks; ECC's hook *taxonomy* (explicit PreCompact hook for state-saving, explicit SessionEnd hook) is more complete than what's confirmed in Hermes | Config/plugin: check whether Hermes has an explicit pre-compaction save-state hook; if not, add one modeled on ECC's PreCompact hook | S | M |
| Memory-persistence hook module (`hooks/memory-persistence/`) | Structured SessionStart/PreCompact/observation/activity-tracking/SessionEnd lifecycle for durable memory | Already have (memory layer v1, per baseline doc) — do not re-port | — | — | — |
| Session-handoff / checkpoint command (`commands/checkpoint.md`) | Explicit slash command to snapshot session state for handoff | Unknown — not read in depth this pass; flagged for follow-up | Hermes command/skill: a `/checkpoint` equivalent writing session state to disk for later resume | S | M |
| `harness-audit.md`, `agent-eval` skill, `benchmark-methodology` skill | Self-evaluation/benchmarking skills for agent harnesses themselves | Already have (evals with history, per baseline doc) — do not re-port | — | — | — |
| Language-specific reviewer/build-resolver agents (the bulk of the 65 agents) | Per-framework (React/Django/Flutter/Rust/Go/Swift/etc.) review and build-fix agents | N/A — Hermes is a Python-stdlib personal agent, not a polyglot coding harness | Not portable — Claude-Code-plugin-specific, out of scope for Hermes | — | — |

### ECC — top ports
1. **Prompt-defense-baseline preamble** — treat fetched/tool/URL content as untrusted; refuse role-override, unicode/homoglyph, and injection tricks; reject before the content reaches the model. Mechanism: bake the boilerplate block from ECC's reviewer agents directly into Hermes's `transform_tool_result` hook as a pattern-match/flag step. Lands in: the hermes-agent plugin file implementing `transform_tool_result`. Effort M, value H.
2. **`verification-loop`-style pre-completion gate** — build/typecheck/lint/test/secret-grep/diff-review sequence before a coding task is marked done. Mechanism: adapt to Python tooling as a new Hermes skill (`SKILL.md`) invoked by the agent before closing out a dev task. Lands in: `~/.hermes/skills/software-development/` (new skill file). Effort S, value M.
3. **`silent-failure-hunter`-style review checklist** — hunt bare excepts, swallowed errors, dangerous fallbacks in Hermes's own Python codebase. Mechanism: a skill file with a Python-flavored checklist (mirrors the JS/TS original). Lands in: `~/.hermes/skills/software-development/` (new skill file), usable ad hoc by the owner on the Hermes repo itself.

## 3. prime-agent — feature inventory

prime-agent (PrimeIntellect-ai/prime-agent, hard fork of `pi-mono`/Mario Zechner's `pi`) is a "RLM-native terminal coding and research harness" whose defining design choice is: **the model gets exactly one tool, `ipython`**, backed by a persistent IPython kernel (auto-bootstrapped venv, or point `PRIME_AGENT_KERNEL_PYTHON` at an existing env with `ipykernel`). Everything else (skills, MCP integrations, custom tools) is exposed *through* that one kernel rather than as separate tool-call schemas. The owner has already ported the core "rlm-repl" idea (persistent IPython MCP server) from this project per memory notes — this pass confirms what's still un-ported.

| Feature | What it does | Hermes has it? | Portable how | Effort | Value |
|---|---|---|---|---|---|
| Single-tool `ipython` design | Model gets one tool; all capability (fs read, bash, data inspection, skill calls) happens as Python code in a persistent kernel — no per-tool JSON-schema bloat | Already ported (rlm-repl MCP server, per memory) | — | — | — |
| Python-backed skills (`SKILL.md` + `src/<import_name>/`) | A skill can ship real Python code the kernel `pip install`s and exposes by import name; model calls it directly or `help()`s it | Partial — Hermes skills are markdown-only (SKILL.md), no first-class "installable Python package skill" | Hermes plugin: extend the skill-loading path so a skill directory with a `src/` package gets installed into the rlm-repl kernel's venv and becomes importable | M | H |
| MCP-as-Python-skill pattern (`McpIntegration` base class) | MCP servers are wrapped as a Python class (`class Acme(McpIntegration)`) imported into the kernel rather than exposed as new agent tool-call schemas, avoiding tool-schema bloat entirely | No — this is a genuinely different MCP integration style than schema-per-tool | Hermes plugin: a `McpIntegration`-style base class for the rlm-repl kernel so MCP servers are called as `await server.tool(...)` inside Python rather than adding to the tool-schema block (directly related to the harness-research.md finding about the 15.5k-token tool-schema block) | M | H |
| Session tree with in-place branching (`/tree`, `/fork`, `/clone`) | JSONL sessions stored as a tree (`id`/`parentId`); branch, label/bookmark entries, filter by tool/user-only/labeled, navigate without creating new files | Partial — Hermes has session persistence (per baseline) but branching/labeling within one file is unconfirmed | Hermes plugin: extend session JSONL format with `parentId` + a `/tree`-equivalent dashboard view; bookmarking (`Shift+L`) is a cheap add | M | M |
| Autonomous-mode gates (`--autonomous-gate <command>`, retry/timeout/turn/token/wall-clock limits) | Host-managed continuation loop that only stops when configured shell-command gates all pass, with explicit per-gate retry/timeout and global turn/token/wall-clock caps | Partial — owner's own `/autonomous` skill + `autonomousctl` (Stop-hook loop) exists but gate-command semantics (shell command must exit 0) are unconfirmed as present | Hermes: add explicit `--gate <shell-cmd>` config to `autonomousctl`'s mission.json schema, modeled on prime-agent's gate/retry/timeout defaults | S | M |
| Extensions API (`pi.registerTool`, `pi.registerCommand`, `pi.on("tool_call", ...)`) | TypeScript plugin surface for custom tools/commands/event-hooks/UI | N/A — Hermes already has its own Python plugin-hook system (`pre_llm_call`, `transform_tool_result`); this is the same idea in a different language, not a new capability | — | — | — |
| Prompt templates (`/name` markdown expansion) | Reusable prompt snippets in `~/.prime/agent/prompts/*.md`, invoked by typing `/name` | Unknown — not confirmed present in Hermes | Hermes: trivial — a `prompts/` directory + slash-expansion in the Telegram/dashboard input path | S | L |

### prime-agent — top ports
1. **Python-backed installable skills** — skills that ship real code (`src/<import_name>/`) get installed into the rlm-repl kernel's venv and become directly importable/callable, instead of markdown-only instructions the model has to re-derive tool calls from. Mechanism: extend Hermes's skill loader to detect a `src/` package alongside `SKILL.md` and `pip install -e` it into the persistent kernel. Lands in: the skill-loading code path used by `~/.hermes/skills/*` and the rlm-repl MCP server config. Effort M, value H.
2. **MCP-as-Python-object pattern** — wrap MCP servers as a Python class imported into the kernel (`await server.tool(...)`) rather than new agent tool-call schemas, directly reducing tool-schema token cost (the harness-research doc's own largest lever). Mechanism: port the `McpIntegration` base-class idea. Lands in: rlm-repl kernel setup / a new `mcp_integration.py` helper. Effort M, value H.

## Contradictions & caveats
- Star counts (GitHub API, pulled live 2026-09-08/09) are self-reported platform metrics, not independently audited for bot/campaign inflation; the "fastest star-growth record" and "20k stars/hour" figures are third-party blog claims (Flowtivity, Pasquale Pillitteri, a Substack post), not from DeepSeek directly — treat as directional, not verified.
- The dsh spike (`~/.hermes/dsh`) and the installed rc.7 CLI are functionally the same harness at the plugin-package level; the only material difference found is the spike's extra client-UI package family (~40 `dsh-client-ui-*` packages) not present in rc.7's shipped CLI dependency tree — this is a UI/packaging difference, not a feature regression.
- Several features are marked "unknown" rather than confirmed absent in Hermes because this pass did not do a full grep of the Hermes codebase for MCP-client support, an explicit pre-compaction save-state hook, or session-tree branching — a code-scout sweep of `~/HermesAssistant` would be needed to confirm before implementing items 4, 5 (ECC PreCompact hook), and the prime-agent session-tree/branching item with certainty.
- ECC's 65 agents and majority of its 285 skills are Claude-Code-plugin scaffolding for polyglot software review/build (React, Django, Flutter, Rust, Swift, etc.) and are explicitly judged not portable to a Python-stdlib single-user personal agent — excluded from the shortlist by design, not oversight.
