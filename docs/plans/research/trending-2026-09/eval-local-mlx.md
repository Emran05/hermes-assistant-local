## (a) MLX serving: can we unpin from mlx-vlm 0.6.14?
**Likely yes, with a re-test.** mlx-vlm has moved 0.6.14 → 0.6.15 → 0.6.16 → 0.6.17 → 0.7.0 (Sept 7, 2026). Verified via GitHub Releases API (high confidence, primary source):
- v0.6.15: "Stop a batched row's answer depending on its neighbour's length" (#1946) — a batching-isolation fix.
- v0.6.16: "Configure KV cache quantization per tensor" (#1807), "fix(server): stop skipping KV cache quantization on 'qat' model paths" (#1955), "Refactor MTP split pathways" (#1935) — this is the version Hermes currently flags as producing corrupt output under concurrent MTP speculative decoding.
- v0.7.0 (current, Sept 7 2026): "Fix native quantized KV in Qwen MTP verification" (#1986), "fix(speculative): detect native MTP drafters via num_nextn_predict_layers" (#2120), "Fix phantom KV in ragged batched speculative rollback" (#2113), "Fix positioned top-k sampling for speculative generation" (#2029), "Fix TurboQuant batch decode, MTP KV quantization, and attention sinks" (#1822), plus "Anthropic route: keep in-conversation system messages in place (fixes prefix-cache defeat)" (#2052) and "Stop a short first prompt from disabling prefix caching" (#1901).
These read as direct fixes for the class of bug (concurrent MTP + KV cache corruption) that caused the pin. **Recommendation: stand up a canary on 0.7.0 (not 0.6.16/17, which the changelog itself shows were still buggy at those points) and re-run Hermes's MTP concurrency eval suite before repinning.** Do not skip straight to unpinning in production; 0.7.0 also carries a large batch of new model support and an MLX-core bump (0.32.x) that could introduce new regressions unrelated to the original bug.
- `ml-explore/mlx-lm` release notes could not be fetched past April 2025 in this pass (GitHub UI truncation) — unknown state for July–Sept 2026; needs a follow-up API pull (`api.github.com/repos/ml-explore/mlx-lm/releases`).
- New serving alternatives worth benchmarking rather than adopting outright: **jundot/omlx** (21.5k★, "continuous batching & SSD caching, managed from the macOS menu bar" — SSD-backed KV/weight streaming is directly relevant to RAM ceilings) and **raullenchai/Rapid-MLX** (3.7k★, Apache-2.0, built on mlx-lm/mlx-vlm/mlx-audio, claims "4.2x faster than Ollama, 0.08s cached TTFT, 100% tool calling" — **self-reported, benchmarked against Ollama not against mlx-vlm directly, unverified**). Neither has been independently verified; treat star counts themselves with caution since several very-high-star repos in this cycle (75k, 35k, 21k created since Feb 2026) look like inorganic/promotional star patterns typical of the current MLX hype wave — do not weight stars as a maturity signal without checking commit history and issue activity directly.

## (b) Local voice path with no new app entitlements
Two concrete, verified patterns exist that let Hermes get voice without touching the frozen WKWebView shell's entitlements:
- **0xbrando/dictate** (MIT, Python 3.11+ + Swift ANE helper, 18★): a standalone menu-bar app + CLI that owns its own Microphone and Accessibility permissions independently, pastes transcribed text at the cursor via the Accessibility API. Quote: "macOS will prompt for Accessibility and Microphone permissions on first run." This is exactly the "separate signed helper" shape Hermes needs — install as a companion app, have it paste into Hermes's Quick Ask popover or push text over localhost, no changes to Hermes's own Info.plist/entitlements.
- **cleanunicorn/earheart** (MIT, Electron, 454 commits): global-hotkey push-to-talk using local Parakeet STT + local Gemma cleanup, auto-pastes into the focused app. Also a separate process with its own mic/accessibility grants. Less attractive for Hermes given the "no Node/Electron in the product" constraint — useful only as a reference for the hotkey/cleanup UX, not as vendorable code.
- Also noted but not deep-read: **Leo6Leo/whispr-stream** (Qwen3-ASR via MLX, Swift, on-device streaming) and **basnijholt/wyoming-mlx-whisper** (Wyoming protocol server for MLX Whisper) — both are candidate STT backends if Hermes later wants voice input piped through its own dashboard rather than a helper app's paste.
Mechanism for Hermes: ship `dictate`-style helper as an optional companion install (Homebrew formula or bundled binary), have it write to a local socket/file that Hermes's dashboard polls, or trigger a Hermes Quick Ask action via URL scheme. Effort S–M, risk low (isolated process, no entitlement changes), capability gain: voice input finally unblocked without a Swift shell rebuild.

## (c) macOS automation / computer-use vs. Hermes's cua-driver
- **wimi321/macos-computer-use-skill** (MIT, TypeScript+Python, 18★, early/v0.2.2): standalone MCP server, "zero private dependencies" (pyautogui/mss/Pillow/pyobjc only), requires Accessibility + Screen Recording permissions on the host process. It is **coordinate-based, not accessibility-tree based** — same fundamental approach as most cua-drivers, no advance over Hermes unless Hermes lacks multi-display/clipboard support.
- **Ashishkosana/agent-hands** ("record-once/replay-many", MIT, Python 3.12+, 1★ but well-documented, 85 tests): the more interesting mechanism — an LLM drives a task once, the successful run is distilled into a typed "capability artifact" (locator ladders, recognizers, checkpoints) that replays deterministically with **zero LLM tokens per replay** and works offline (verified via subprocess isolation stripping API keys). Currently Playwright/web-surface only; schema is "surface-neutral" so a macOS accessibility-tree backend could in principle be swapped in. This is the most promising idea to port: for Hermes's repeated inbox-triage/automation flows, a discovery-once/replay-many capability cache would cut both TTFT and tool-budget spend versus a live vision loop every time. Effort M (needs a macOS-native locator/recognizer backend), risk medium (replay staleness when UI changes — the project's own "recognizers poll for expected state" pattern is the mitigation to copy).
- **zouyuanqing/vision-primitives-mcp** was found in the search but not deep-read; flagged as a text-only-LLM vision helper (describe/locate/OCR/crop/zoom) — relevant if Hermes ever runs a model without native vision.

## (d) MCP servers a personal Mac agent should ship with
- **fellowgeek/mcp-memory** (MIT, Python, 211★): OKF v0.2-compliant persistent memory server over SQLite+FTS5, "sub-20ms key lookups." Significant conceptual overlap with Hermes's existing Mail/Messages FTS5 memory layer — not a clear net-new adoption, but its OKF markdown-dump dual-layer (human-readable + queryable) is a pattern worth borrowing for Hermes's memory export/debug story. Low priority given overlap.
- **okf-memory/okf-agent-memory** (Go, 491★, created Sept 5 2026 — days old, extremely fast velocity): "Git-native persistent memory for AI coding agents," OKF v0.2, sub-300µs in-memory BM25, embedded MCP server. Worth a follow-up pass; too new to assess maturity (unknown, low confidence on any claim).
- **kerlenton/mcpsnoop** (347★, Go): "Wireshark for MCP" — transparent proxy showing every tool call live. Useful as a debugging/trace companion for Hermes's existing traces feature; low-effort adoption (run as sidecar, no code change).
- **fkiene/llmtrim** (229★, Rust, MPL-2.0): local proxy that compresses LLM API requests/tool output to cut tokens "with no change to the answers" — same problem space as MineEcho's TokenLess (see (e)), but shippable as a drop-in local proxy rather than a library port. Worth benchmarking against Hermes's own prompt-token budget.
- General MCP servers relevant to a personal-agent bundle but not deep-read this pass: `mrpulor-gh/nuphus-mcp` (desktop automation MCP for screen/window/mouse/keyboard + Chrome), `zanei` (local activity-context MCP), `figwright` (Figma), `ripwire` (repo-search-for-agents CLI+MCP). None verified beyond description.

## (e) FABULA's gates/judge/proof-of-done vs. MineEcho's compression — what Hermes's harness lacks
- **sergezuber/FABULA-LLM-5** (MIT, Bun/TypeScript, 83★): enforces "done" as a test result, not a prompt claim. Mechanism (verified from README, medium confidence — no independent test of the claims): a **Verify** gate blocks completion until the project's own tests actually run and pass; a **Reproduce** gate rejects a "fix" whose tests also pass unmodified (i.e., catches false positives / no-op patches); an independent **Judge** vetoes premature end-of-task claims; a **Rewind** gate auto-reverts to last-green state after repeated failures. Every run mints a "Proof-of-Done receipt": diff + verification command + model ID + SHA256 context fingerprint, making runs replayable/auditable. Quote: "Done is a test result here. After a source edit the engine re-enters the turn until the project's own tests actually ran — in the run loop, not in a prompt." **Hermes's evals/traces/doctor cover observability but nothing here appears to gate task completion on independent verification or produce a signed receipt** — this is the clearest gap. Port as an idea (stdlib Python state machine wrapping tool-call loop: verify → judge → rewind → receipt), not vendored code (Bun/TS, product forbids Node). Effort M, risk low, benefit: reliability on multi-step tasks with small local models, which is exactly Hermes's hard case (Qwen3-class models via mlx-vlm).
- **Health-Yang/MineEcho** (source-available, PolyForm Noncommercial — **not usable to vendor into a product without a commercial license**, TypeScript/Node 22+): "TokenLess" context compression keeps errors/counts/head-tail/actionable lines instead of truncating blindly, with "15 built-in reducer rules for git, npm, cargo, docker, document extraction, and generic long output," claiming a self-reported "20%-85% token-saving range." The mechanism (structured reducers per tool-output type, rather than naive truncation) is portable as an idea into Hermes's tool-budget layer even though the code itself is license-blocked and off-limits (Node runtime anyway). Effort S (reimplement 5-10 reducer rules in stdlib Python for Hermes's actual tool set: shell, grep, git, mail/Messages FTS5 dumps), risk low, benefit: directly reduces prompt tokens fed to small local models — Hermes's stated small-model constraint makes this higher-value than for a cloud-model harness.
